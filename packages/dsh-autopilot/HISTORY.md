## Что делает

Автопилот ведёт проект от требований и плана через задания, разработку и review к итоговой проверке. Мастер хранит состояние проекта и закрепляет каждый RUN на физическом runtime. Исполнители получают задания через почту, а оператор читает этапы, карточки задач и результат на статической панели. Проектная память, задания и история остаются в проекте; полномочия исполнителя задаются его действующими инструкциями и нарядом.

Наш слой добавляет к upstream серверные права и pin, общий каталог прогонов, почтовый транспорт, безопасную публичную проекцию и раздачу. Измерение расхода привязывается к источникам runtime/движка и квитанции; текст ответа модели числовым источником не служит.

## Устройство и отличия от upstream

Runtime устанавливается офлайн в root-owned `sources/releases`; Мастер работает через physical pin и operator lock. `current` выбирает runtime для нового init; последующие события существующего RUN используют его физический pin. Публичные state.js/HTML строятся по разрешённой схеме с фильтрацией секретоподобных строк и обслуживаются общей раздачей. Почта проверяет Unix-отправителя и TLS-сервер; квитанции доставки и измерения относятся к разным этапам.

Письма Мастера и маркер `AUTOPILOT-PILOT` не расширяют права исполнителей. При общем UID полной изоляции нет; G4 проверяет заявленные счётчики, а независимость проверяющего требует отдельного подтверждения.

## Пути и команды Мастера

```text
/opt/autopilot/sources/<upstream-sha>/                 архив исходника
/opt/autopilot/releases/<upstream-sha>-<revision>/      физический runtime
/opt/autopilot/current -> releases/...                выбор для нового init
/opt/agent-skills/autopilot -> /opt/autopilot/current/skill
/srv/autopilot/public/<agent>/<projectUUID>/<runUUID>/  dashboard.html и state.js
/var/lib/dsh-autopilot/                               каталог закреплений run
```

От Unix-учётки `master`, в физическом корне **разрешённого** проекта:

```sh
REL=$(realpath /opt/autopilot/current)
python3 -B "$REL/skill/tools/ap.py" --no-serve init --slug example --skill-dir "$REL/skill"
```

Для дальнейших событий берётся `state.js['_sadik']['release']['skill_dir']`, а не новый `current`. Например, у уже закреплённого run:

```sh
python3 -B "$PINNED_SKILL/tools/ap.py" --no-serve commits
python3 -B "$PINNED_SKILL/tools/ap.py" --no-serve finish --result 'проверенный итог'
```

`PINNED_SKILL` берётся из настоящего private `.autopilot/state.js`; это не поле письма или произвольная подстановка. Root не оператор. Неизвестные команды/флаги отвергаются, `--dry-run`, `-n`, `--check` не являются режимами AP runtime. Не удалять `operator.lock` и не подменять pin вручную. `commits` сохраняет state и может дать предупреждения при rc0; это не самостоятельная приёмка кода.

`README-PILOT.md` описывает разные точки входа: операторский helper в physical core и receiver helper в postal runtime. Они не взаимозаменяемы. Не использовать старые примеры с `--name alfa`, чтением письма из stdin в `receive` или отправкой `a2a-send` вместо текущего postal transport.

## Панель и карточки

В установленном 0.1.8 панель показывает этап, задания, ожидания и итог RUN. Заголовок завершения читается вместе с `result`: завершённый RUN может иметь отрицательный результат. Публичная карточка прежнего расхода этой версии ограничена Codex, даже если private-снимок Claude сохранён.

В сборке 0.1.9 панель Марка сохраняет этапы подготовки, требований, брифинга, спецификации, плана, разработки, review и приёмки; карточки показывают ход задания, review, ремонт и отказ. Есть RU/EN и темы оформления. Это описание кандидата интерфейса, а не заявленная браузерная приёмка всей ещё не сведённой сборки.

Старые карточки `usage` и командная квитанция `usageTeam` рисуются независимо рядом. Codex подписан «Поток оператора», при соответствующем охвате — с найденными дочерними потоками; валидный observed Claude — «Сова · указанные запросы». Их шесть чисел, собственные окна и время измерения сохраняются. Неизмеренный/негодный Claude не выдаётся за измеренный. Командная строка при отсутствии привязки пишет «неполно: нет R/G», называет участника и причину; старые карточки не становятся суммой всей команды.

## Счётчики и граница доказанного

### Прежние снимки 0.1.8

Корзины Codex и Claude раздельны. Снимок v1 хранит шесть метрик: modelCalls, inputTokens, uncachedInputTokens, outputTokens, cacheReadTokens и cacheWriteTokens; вместе с ними — источник, окно, measuredAt и охват. Root-путь Claude и writer требуют защищённый снимок; при ручной публикации Мастер использует физический pin своего RUN. `null` означает отсутствие измерения, повторный снимок не прибавляется заново. Договоры: [FORMAT-CONTRACT.md](FORMAT-CONTRACT.md) и [tools/README-usage-snapshot.md](tools/README-usage-snapshot.md).

### Онлайн-квитанция кандидата 0.1.9

Потребитель рассчитан на Claude **и** Codex. Root связывает run/project, задания из AP-почты, R-факты runtime и G-факты фактических запросов движка с raw-источниками. Парсеры читают их под UID/GID владельца без дополнительных групп; доступ Мастера к чужим HOME для этого не расширяется. Данные модели и вручную выбранный текущий слот подписки не заменяют эти доказательства.

Командная квитанция v2 имеет строки **участник × движок × подписка**, шесть метрик и «из них субагенты». Последнее — подмножество общего итога, а не ещё одно слагаемое. `basis=closed_turns`: незакрытые ходы остаются в `pending`, их текущая стоимость сюда ещё не включена. `asOf` — доказанный срез источников, `measuredAt` — время измерения; старше 120 с панель отмечает устаревание.

Один недостающий участник или недоказанная привязка делает проект `incomplete`: шесть общих totals равны `null`, причина и имя сохраняются, подтверждённые строки остаются видны. Отсутствующий источник не превращается в ноль. Квитанция root связывается с реальным путём проекта; не-модельный writer под UID master и operator.lock публикует её, сохраняя задания, gates и состояние оператора.

В поставке кандидата есть root timer с интервалом 60 с. Без OPEN (открытого RUN в корневом индексе учёта) он читает только usage-индекс, без обхода HOME. Это отдельный индекс учёта, не каталог закреплений `/var/lib/dsh-autopilot`. Нормализация R и CLI register подготовлены и испытаны на копиях; **живой зовущий root register до первого AP init и полная G-ступень ещё не сведены**. Полный онлайн-учёт команды в бою этим не объявлен.

### Границы сборки 0.1.9

- **R и размер.** Prep пока перечитывает источник целиком. В копийной выборке одного получателя соотношение 1 request/turn даёт верхнюю R-only оценку около **12,7 тыс. запросов** до 16 MiB (оценка по копии, не замер живого среднего). Общий бюджет также расходуют остальные источники и heartbeat, поэтому неполнота возможна раньше. Raw R допускает 128 MiB; это не означает, что нормализатор сможет обработать столько за проход. После превышения бюджета возможен постоянный `BUDGET_EXCEEDED`; инкрементальная обработка пока предложение, не готовая функция.
- **source_gap.** TG — плагин `dsh-telegram-multiagent`, в котором работает поставщик R. В принятом R для сводного выпуска (TG 3.1.13) причина защёлкивается до рестарта TG; новые requests её не снимают. Для доказанного учёта нужны рестарт и подтверждённое восстановление/сверка источников (сверка источников в этом выпуске не реализована). После рестарта новые прогоны могут стать полными при согласованных источниках и подтверждённой полноте. Прежние затронутые окна полными не становятся: исторический gap сохраняется. Если источник снова ломается, снова возникает gap; один рестарт не обещает устранения причины. Рестарт выполняется отдельным назначенным окном.
- **G и Codex-слот.** До принятой G-привязки исторического credential handle/epoch слот Codex остаётся `UNBOUND`/`SUBSCRIPTION_UNBOUND`. Текущий registry или symlink не доказывает подписку прошлого запроса. Полный G и register-caller — открытые части сведения.
- **Субагенты.** Текущий онлайн-потребитель не поддерживает native Claude Agent/Task и native Codex spawn: обнаружение даёт именованную неполноту. Для DSH spawn полный охват также не заявлен. Причины — `CLAUDE_NATIVE_SUBAGENT_UNSUPPORTED`, `CHILD_SOURCE_UNSUPPORTED`, `CODEX_NATIVE_SUBAGENT_UNSUPPORTED` либо `UNLISTED_CHILD`; subtotal детей при такой неполноте равен `null`. Наличие graph-данных само по себе не включает поддержку: потребуется отдельная принятая согласованная дельта AP-потребителя и R/G.
- **Время и полнота.** Общий source-бюджет итерации 16 MiB; подготовка R имеет cooperative 3 с. Systemd-служба ограничена 35 с, что не гарантирует свежую квитанцию при убийстве. Пропуски, неподдержанный формат и недоказанные границы хода остаются неполнотой по имени; job после 7200 с получает JOB_OVERDUE без отмены её работы. Эти счётчики не являются финальным drain или счётом провайдера.

## Установка и выпуск

Базовому установщику нужны Linux, Bash и **Python 3.10+ со stdlib**; runtime-операциям нужен Git. Docker и npm lifecycle-установка для нашей схемы не нужны. Требования к учёткам и отдельным службам приведены ниже.

### Требования к другому серверу и пример sadik

Разделы выше — **пример нашей раскладки на sadik**, снятый 17.10.2026, а не результат установки на произвольный сервер. Версии mail/copy, адреса ap1, имена участников и назначения Забавы/Искры описывают этот профиль. Прежде чем выполнять команды установки, администратор другого сервера готовит следующие условия:

| Область | Что требуется подготовить |
|---|---|
| ОС и инструменты | Linux, **Python 3.10+ со stdlib**, в том числе `/usr/bin/python3`, Bash, Git, `realpath`, `getent` и `groupadd`. Для запуска поставляемых служб нужен systemd. Python 3.9 не входит в заявленную совместимость; флаг `-B` не снижает этот минимум. |
| Оператор | Заранее созданная непривилегированная Unix-учётка **`master`**, её рабочий HOME и разрешённый Git-проект. Имя `master` проверяется кодом, это не свободная метка из примера. Установщик эту учётку не создаёт; root предназначен для установки, не для событий AP. |
| Читатель панели | Группа **`autopilot-view`**; `master` не должен входить в неё ни основной, ни дополнительной группой. Применяющий установщик создаёт группу, если её нет, и готовит public-каталоги; доступ службы-чтеца администратор настраивает отдельно. |
| Каталог запусков | Для release с каталогом `/var/lib/dsh-autopilot` нужна отдельная принятая инвентаризация и root-bootstrap по договору этого release. Одного существующего каталога недостаточно. Базовый `install.sh` размещает runtime, но этот bootstrap не выполняет. |
| Почтовый профиль | Для работы почты нужны отдельные `autopilot-post` и `autopilot-copy`, группа `autopilot-mail`, учётки команды, конфигурация сокета/TLS, notice-профили и настроенные боты. Текущий helper закрепляет шесть имён: `vintik`, `shpuntik`, `gayka`, `shurup`, `sova`, `tumbler`; другой состав требует отдельной адаптации и приёмки. Договор и предварительные условия — в README-CORE.md и MAIL-LAYOUT.json. |

Значения `192.168.99.6:8787` и `ap1.insmat.ru` — наш пример, не универсальная настройка. Владелец другого сервера назначает своих администратора монтажа, оператора и принимающего; имена наших агентов не заменяют эти роли. |

`npm install` не настраивает эту инфраструктуру. Базовый `install.sh` не создаёт DSH-агентов, их сессии, почтовые профили, ботов и TLS-развёртывание и не включает/не перезапускает службы. README-CORE.md и README-PILOT.md описывают отдельный почтовый контур нашего профиля. При отсутствующих предпосылках нельзя считать размещённые файлы готовой внешней установкой. Тестовый профиль тоже требует подготовки: `test/stend-dsh-autopilot.sh` создаёт root/UID-фикстуры и задаёт `AUTOPILOT_TEST_SKILL`/`AUTOPILOT_TEST_UPSTREAM`; голый `unittest` или `npm test` не заменяет этот полный стенд.

### Окно 0.1.8: каталог прогонов, census и ограда

Одного `install.sh` недостаточно: bootstrap каталога выполняется отдельным принятым шагом окна. На sadik каталог уже создан. `/var/lib/dsh-autopilot/legacy.json` хранит принятый root-census, `bootstrap.json` связывает его сумму с поколением и окном, `applicability.json` отмечает применимость, а `runs/catalog.json` ведёт текущие закрепления. Root создаёт опору; Мастер меняет разрешённую часть под общим `run.lock`. Наличие папки без этих связей не означает готовность.

Для первичного создания каталога 0.1.8 при отсутствующей опоре порядок такой: подготовить принятую физическую полку и страховки; включить ограниченную ограду; снять и принять полный owner-census без активных runs и record с признаком `potentialProductionPin`; установить runtime и выполнить bootstrap; отдельно проверить права, повторный scan и соответствие census; выполнить предусмотренную листом пробу и снять свою ограду. Census включает все видимые локальные файловые системы и признаки владельца/pin, а не только `/opt/master`. Уже существующий каталог оконный helper заново не создаёт; последующие обновления и замена поколения выполняются по отдельному принятому договору.

Неполный или неизвестный источник не даёт допуска. Оконное сравнение изменившегося состава сообщает `CENSUS_RAZOSHLIS` с кодом 1; отказ предпосылок — `ОТКАЗ`, код 2. Проверка опоры самим runtime-каталогом использует `RUN_INVENTORY_UNPROVEN`. Эти исходы не следует объединять одним обещанным кодом ошибки.

Ограда прямого окна останавливает процессы оператора через freeze двух его юнитов и проверяет их native idle, PID/starttime и полный состав UID. Её transient-держатель имеет RuntimeMaxSec; в helper по умолчанию 900 с, допустимо 5–1800 с, перед bootstrap/сравнением должно оставаться не меньше 120 с. Истечение или снятие держателя освобождает его freeze. Это снимки и ограничение доступа штатного оператора; короткий привилегированный запуск между снимками и параллельные действия root этим не исключаются. Команды ограды не следует выполнять отдельно от принятого листа.

Legacy-ядро не поддерживает общий протокол каталога. Его выбор требует отдельного допуска, а применимость каталога отмечается `inapplicable`; восстановление требует нового принятого census/bootstrap. Смена `current` не переносит существующий run на другое ядро и не переписывает его pin.

### Команды принятой установки

Из **принятой полки**, администратором монтажа после приёмки:


```sh
sudo bash ./install.sh --dry-run
sudo bash ./install.sh
sudo bash ./install.sh --check
```

Это справочник установщика, не команда обновить бой из текущего master. `--dry-run` выводит план, `--check` сверяет без ремонта; они не создают lock/каталоги, не генерируют ключ и не меняют NSS. Для check код1 означает нужный ремонт, код2 — отказ. Это флаги установщика, не AP runtime. В этой ветке `package.json` задаёт кандидат 0.1.12, а `source-lock.json` — его immutable target; порядок установки — [лист П 0.1.12](window/LIST-P-0.1.12.md). установленный `current` в срезе sadik 17:07 UTC — `a17-b9-c2-rollback-r2` (0.1.8). При сведении 0.1.8 лицензионные шапки изменили байты release, поэтому был назначен **новый immutable ID** `a17-b9-c2-rollback-r2` вместо принятого `a16-b8-c2-rollback-r2`; для новых байтов кандидата 0.1.9 назначен отдельный ID `a20-b15-c2-team-online`. Повторно использовать имя принятой полки для новых байтов нельзя. Номер в дереве/принятый кандидат и факт монтажа различаются. `DESTDIR` — отдельная проверенная root-owned fixture, не песочница против её владельца; raw sources не исполняются.

0.1.5, 0.1.6 и 0.1.7 — история; 0.1.8 установлен ([CHANGELOG.md](CHANGELOG.md)). Сводный 0.1.9 подготовлен кандидатом; полное сведение G и register-caller ещё не завершено. Папка `/srv/autopilot/projects` на sadik пока отсутствует; её появление и запуск полного онлайн-учёта требуют собственного принятого окна. Автоматическая миграция pinned run, общий sandbox исполнителей и биллинг провайдера в этот выпуск не входят.
