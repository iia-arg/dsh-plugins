# measure-run-codex — замер прогона Autopilot по журналам Codex

Адаптер к upstream `tools/measure-run.py` (nick-vels/skills 9fc898cb): переводит журналы Codex оператора и его
субагентов в раскладку Claude Code во временном HOME и зовёт неизменённый `measure-run.py`. Единица («шаг» — один
вызов модели), формулы и вид отчёта — upstream.

```
sudo -u master python3 <physical-release>/tools/measure-run-codex.py --measure-run <sources/<sha>/tools/measure-run.py> \
  --codex-home /var/lib/coder-gateway-master/codex-home --potok <id потока> [--s <ISO>] [--po <ISO>]
```

- **Только от владельца CODEX_HOME** (`sudo -u master`, учётка кодера), **никогда от root**: euid 0 → отказ, код 2.
- `measure-run.py` принимается только с закреплённой sha256 (`ZAKREPLENO` в коде — 9fc898cb); иная — отказ 2.
  Исполняется проверенная копия байтов во временном HOME, а не файл по пути.
- Цикл в родстве потоков (`parent_thread_id`) — отказ 2 с причиной.
- 🔴 Отчёт и временные файлы несут дословный текст exec-команд оператора и исполнителей — наружу без просмотра не
  пересылать. Временный HOME (`$TMPDIR/measure-run-codex-*`) убирается при обычном выходе; SIGKILL его оставляет.
- Проверка числа шагов вторым срезом (разные учёты в `event_msg token_count`) — проверка ПЕРЕВОДА, не полноты: оба
  среза читают один и тот же журнал и одинаково слепы к вызовам, которых в нём нет.

- **Полнота — `--sverka-shlyuz`** (по умолчанию выкл). Шлюз 3.1.5 пишет итог каждого хода из уведомлений app-server
  `thread/tokenUsage/updated` (канал протокола, НЕ файл rollout) в `$CODEX_HOME/dsh-usage-hodov.jsonl`. Адаптер сравнивает с
  ним число вызовов и суммы input/cached/output/reasoning записей журнала Codex того же `turn_id`: расхождение — «пробел
  журнала: turn …», код 1; нет файла шлюза, ход без итога шлюза или законченный ход, начатый ПОСЛЕ монтажа шлюза 3.1.5,
  без его строки — СЛЕПОТА, код 2. Момент монтажа — `--s-shlyuza <ISO>` (время монтажа из журнала окна) или, по умолчанию,
  ts первой строки файла шлюза (верхняя граница монтажа: ход между монтажом и первой записью, потерявший строку, по
  умолчанию не виден — для приёмки окна давать `--s-shlyuza`). Только корневой поток: шлюз видит уведомления своей нити,
  субагентов Codex — нет.
- 🔴 **Граница сверки:** уведомления и rollout пишет один процесс codex — сверка ловит потерю журнала, не ошибку счёта
  usage в codex (и это не учёт провайдера).

Не ловит: исполнителей через почту (их потоки — в других CODEX_HOME, не потомки оператора); вызовы, которых нет в
журнале; инструменты — приближённо (exec с exec_command → Bash, apply_patch → Edit по «*** … File: <путь>»).
Проверка поставки: `python3 -B -m unittest discover -s test -p test_composition.py -v`; поведенческая проба на копиях журналов описана в листе окна0.1.5.

В выпуск0.1.5 инструмент входит как `<physical-release>/tools/measure-run-codex.py`.
Вызывающий — Мастер вручную в финальной фазе из своего хода, не таймер и не exporter.
Stdout — отчёт; сохранять через `umask 077` в частный файл вне публикуемой `.autopilot/`.
`state.js` и панель этот вывод не читают. Один вызов≤60с (`timeout -k 2s 60s`), повторов0.
Справка сама по себе не доказывает замер; проверяй rc и строку полноты.

Замер делается из следующего хода по уже завершённым ходам; `--po` — время последнего завершённого итога шлюза. Текущий незавершённый ход не включать. Если его usage попал в выбранное окно без итога шлюза, сверка возвращает слепоту2.

В0.1.6 `--snapshot-json --run-id <state-run-id>` с явными `--s/--po` выдаёт числовой snapshotv1; этот режим не исполняет upstream и не парсит его текст. Он требует явные usage-поля, сверку gateway и целые завершённые ходы. Writer `ap.py usage codex --snapshot FILE` и две корзины панели описаны в `README-usage-snapshot.md`. Старый текстовый stdout сам вstate не попадает.
