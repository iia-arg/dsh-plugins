# Защиты, читатели и стенды · Guards, readers and test stands

## Кто вызывает и кто читает · Callers and readers

Ядро не устанавливает systemd-таймеры. Его встроенные проверки вызывает конвейер записи, методы чтения и загрузка плагина; stderr должен собирать процесс платформы. Оператор читает журнал платформы, секретарь читает исход записи, восстановитель читает доверие, внешний планировщик читает отчёт очереди. Заранее назначь каждого из этих читателей в своей установке.

The core installs no systemd timers. Its built-in checks are called by the write pipeline, retrieval methods, and plugin startup; platform stderr must be collected. An operator reads platform logs, the secretary reads write outcomes, the restore plugin reads trust, and an external scheduler reads queue reports. Assign each reader in your own deployment.

## Особый риск разрешающего обработчика · Approval-granting handler risk

`otvechatNaSprosRazresheniya=true` включает обработчик запросов, который разрешает их; это не интерактивный запрос человеку. Он считает вызовы и проверяет факт регистрации через функцию удаления. Позиция в цепочке слушателей изнутри не подтверждается, а политика `never` может отказать раньше обработчика.

`otvechatNaSprosRazresheniya=true` installs a handler that grants requests; it is not an interactive question to a person. It counts calls and checks registration through the returned disposer. Its position in the listener chain cannot be verified internally, and a `never` policy may refuse before it runs.

Не включай ключ ради устранения любого отказа инструмента. Сначала выясни, нужен ли настоящий человек, какой scope спрашивает и какой класс записывается. Счётчик «спросов 0» не доказывает, что никто не запрашивал разрешение: обработчик мог не быть достигнут.

Do not enable the key merely to remove arbitrary tool failures. First establish whether a real person is required, which scope requests approval, and which class is written. A count of zero does not prove there were no approval requests: the handler may never have been reached.

## Загрузка и горячее применение · Startup and hot apply

Свидетель использует возраст процесса: старше 30 секунд — горячее применение, для которого не требуется след старта службы. При свежем процессе ищется запись внешней обёртки в пределах 120 секунд от вычисленного старта. Отсутствие заданного следа означает «не проверено»; неверный след не превращается в доказательство исправности.

The witness uses process age: more than 30 seconds means hot apply, which needs no service-start trace. For a fresh process, it looks for an external-wrapper entry within 120 seconds of the calculated start. An unconfigured trace means unverified; a wrong trace is not treated as evidence of health.

## Запуск стендов · Running stands

```sh
npm test
node test/stend-politiki.mjs
node test/stend-hranilishcha.mjs
node test/stend-ocenki-modeli.mjs
```

Все стенды исполняй на копии пакета и синтетических базах. Перед первым запуском прочти предусловия выбранного файла: отдельные стенды сверяют соседние модули, профиль или внешние артефакты. Общий прогон сохраняет различие `0/1/2`, а итоговой проверкой считается фактический список вызванных стендов, не только код оболочки.

Run stands on a package copy with synthetic databases. Before the first run, read the selected stand's prerequisites: some compare adjacent modules, a profile, or external artifacts. The suite preserves `0/1/2`, and the actual list of executed stands is evidence, not merely the shell's exit code.

Различающая проверка должна пройти исправное → внесённая порча → восстановление. Доказывай порчу числом замен и суммой файла; не меняй боевую базу, чтобы проверить отказ. Для документационного выпуска дополнительно сравнивай JavaScript AST и токены после исключения комментариев; это не заменяет поведенческий стенд при будущей правке реализации.

A discriminating check must cover healthy → confirmed mutation → restored. Prove mutation with replacement counts and a file digest; never corrupt the production database to test failure. For a documentation-only release, also compare JavaScript AST and tokens after excluding comments; this does not replace behavior tests for later implementation changes.

Формат sledPodyomov: `YYYY-MM-DD HH:MM:SS UTC | ДО | <agent>.service | ...` либо `ПОСЛЕ` вместо `ДО`. `<agent>` должен совпадать с config.agent; сообщение с другим именем службы или произвольный startup.log не является подходящим следом.

The sledPodyomov format is `YYYY-MM-DD HH:MM:SS UTC | ДО | <agent>.service | ...`, with `ПОСЛЕ` also accepted instead of `ДО`. `<agent>` must match config.agent; a different service name or arbitrary startup.log is not a valid trace.
