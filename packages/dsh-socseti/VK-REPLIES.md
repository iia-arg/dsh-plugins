# Ответы Анны в ВК

Версия пакета — manifest (3.1.8). Прежний номер ниже — история участка, не версия нынешнего приложения. Общие настройки/статус — [REFERENCE](REFERENCE.md); приёмка живых API выполняется отдельно.

Версия 1.3.1. Вызывающий — `main.mjs` в том же процессе `socseti-anna`, один такт каждые 5 секунд. Настройка writer и ответы выключены по умолчанию. Человек одобряет точную карточку, версию и hash через существующий Telegram callback; одобрение любого из троих допустимо. Модель может создать черновик, но не одобрить его.

## Настройка назначенной рукой

К принятой конфигурации Анны добавляется:

```json
"writer": {
  "enabled": true,
  "token": {"passRef": "vk/user-token-miniapp"},
  "replies": {
    "enabled": true,
    "unknownReplyObjects": ["comment:-127999849:123:456", "dm:789:10"]
  }
}
```

Это фрагмент `vk`, а номера объектов — пример, не боевой перечень. Комментарии и посты используют пользовательский ключ; личные ЛС — существующий `vk.groupToken`. Значения ключей остаются в памяти/HTTPS body, не попадают в argv, журналы или пакет. Pass читается от учётки службы с пределом 5 секунд. Эта настройка не выдаёт новых прав API и не доказывает их наличие.

`unknownReplyObjects` заполняется по инвентаризации неизвестных исходов старого Острова. Канон: `comment:-127999849:<post_id>:<comment_id>` или `dm:<peer_id>:<conversation_message_id>`, без суффикса редакции. Нет поля — статус `legacy_inventory_missing`, ответов по HTTP нет. Пустой список допустим только после проверки монтажной рукой отсутствия таких объектов. Совпадение держит ответ даже после нового одобрения; иной редакционный hash того же объекта не обходит барьер. Собственные sending/accepted/unknown/verification_held для объекта также блокируют новый ответ. Барьер ограничен названными объектами и своей базой, он не инвентаризирует Остров автоматически.

## Адрес и результат

`wall.createComment`: только `owner_id=-127999849`, `from_group=127999849`, `post_id` и `reply_to_comment` из сохранённого события, текст одобренной версии и устойчивый guid. `wall.post` сохраняет `owner_id=-127999849`, `from_group=1`. `messages.send`: только `group_id=127999849`, `peer_id` из события, текст и устойчивый положительный random_id; `from_group` не передаётся. Изменённые/лишние поля, чужой аккаунт, неподтверждённое событие, неизвестный метод, вложения и групповой чат отказаны до HTTP.

Перед реальной отправкой после ожидания общей очереди токена повторно читаются текущие draft/version/hash, допуск, срок, связка с событием и состояние операции. Claim и завершение условны; recovery превращает незавершённую отправку в unknown. Поздний ответ не стирает unknown и не разрешает новую отправку. Прямой API-класс проверяет адрес отдельно от worker. Эти правила касаются программного writer; встроенные инструменты движка по решению владельца не изолированы.

Ответ API — только `accepted_pending_verify`. Отдельные чтения `wall.getComment` или `messages.getHistory` подтверждают идентификатор, автора сообщества, адрес, текст и связь с исходным запросом. ЛС с response=0 сверяется по устойчивому random_id и положительному conversation_message_id. Повреждённый сохранённый request держится без readback. Уже принятая запись сверяется без нового одобрения/его читателя и без требования неистёкшего срока. Максимум 3 устойчиво учтённых попытки чтения, затем `verification_held`; историей ЛС покрыты последние 200 сообщений, непопавшее в этот предел не объявляется доставленным. Unknown записи не повторяются. Ошибка API считается известным отказом только при целочисленном положительном error_code и отсутствии response; потерянный/противоречивый ответ остаётся unknown.

Чтение/запись одного токена делят темп 350 мс после предыдущего завершения. Deadline до 30 секунд включает ожидание; остановка до HTTP удерживает известную неотправленную запись, после начала возможен unknown. Три подряд отказа preflight останавливают worker. `stop()` ждёт активный такт перед закрытием базы. Readback не повторяет запись и не даёт гарантию мгновенного обнаружения всех результатов.

Статус `vk_reply` читает очередь и сообщает `scope=vk_comment_and_private_dm_replies`, ready, halted и причину отсутствующей инвентаризации. Журнал называет draft и исход без текста/ключа. Ready означает готовность этого worker, не успешную доставку всей очереди и не полноту перехода Острова. Общий сторож Анны, поимённая сверка переходного окна, живые права ключей и мониторинг остаются отдельными частями наряда.

Пакет должен идти с полным ранее принятым каналом 3.1.6. Старый 3.1.5-b2027-anna1 на основе 3.1.4 применять нельзя. Автор не монтирует и не принимает свою правку: П7 → Забава → Вениамин → монтаж назначенной рукой.

## Проверка падения писателя постов

`test/vk-post-writer.test.mjs` запускает отдельный `vk-post-crash-worker.mjs` с настоящим Store и writer. Ребёнок коммитит sending/publishing и остаётся перед HTTP в очереди токена; родитель независимо читает эти строки и завершает ребёнка SIGKILL. Новый экземпляр writer восстанавливает unknown и не начинает HTTP. Проба обязана отвергать recover sending→queued даже когда второй слой уже удерживает unknown-черновик. Отдельный случай с queued-действием и прежним действующим approval при unknown-черновике также даёт HTTP0. `valid()` требует approved_held_stage3 до claim, publishing допускается только в beforeSend того же действия; CAS не разрешает позднему результату переписать unknown.
