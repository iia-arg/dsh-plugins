# Сторожа и проверки · Guards and checks

## Кто читает · Consumers

Gateway runtime пишет package/version/source fingerprint, provider, SDK selection и диагностические исходы каждого хода. Pressure watcher читает SDK context/rollout, а operator читает журнал и health. Сам `/health` не обращается к vendor API: healthy credentials могут сосуществовать с неисправным SDK/import или недоступной подпиской.
Gateway runtime logs package/version/source fingerprint, provider, SDK selection and per-turn diagnostics. Pressure watchers consume SDK context/rollout while operators inspect logs and health. `/health` does not call vendor APIs: readable credentials can coexist with a broken SDK/import or unavailable subscription.

| Проверка · Guard | Что ловит · Detects | Граница и читатель · Boundary and consumer |
|---|---|---|
| Проверка входа · Ingress admission | Отсутствие/неверный ключ до SDK · Missing/wrong 64 hex key before SDK | Loopback не является UID firewall; auth failures в HTTP/log · Loopback is not a UID firewall; failures in HTTP/log |
| Беседа v2 · Conversation v2 | Разделение ID/поколения/cwd/provider · ID/generation/cwd/provider separation | Legacy v1 слабее; mapping отдельно от rollout · Legacy v1 is weaker; mapping is separate from rollout |
| Task-control | Binding/повтор/закрытый route · Exact binding/replay/expired route | Accepted ACK не доказывает понимание модели · Accepted ACK does not prove model understanding |
| Pressure | Изменение окна/резерва/порога и слепота · SDK window/reserve/threshold changes, blind-turn streak | Распознавание зависит от SDK fields; restart теряет streak · Detection depends on SDK fields; restart loses streak |
| Подмена модели · App-server reroute | Подмена модели по событию и interrupt · Model change event followed by interrupt | Выданный до события текст не отзывается · Already-emitted text cannot be retracted |
| Image envelope/history | Пределы/протокол/owned cleanup · Bound bytes, protocol, owned checkpoint cleanup | Не стирает user images; проверять физический transcript · Preserves user images; verify physical transcript |
| Статус SDK helper · SDK helper status | SDK диск/версия/журнал/дубли · SDK disk/version/journal/duplicates | Не проверяет живой vendor turn; публичная семья gateway@ включена · No live vendor turn; public gateway@ family included |

Три последовательных model/mapping отказа вызывают deployment alert helper; его путь закреплён кодом. Проверьте наличие команды и назначенного получателя. Отказы фильтра содержания поставщика (тексты «flagged») считаются отдельным видом: два отказа одного вида подряд или один «this session» помечают беседу, и на беседу уходит один сигнал «нужен /new» оператору (alert helper) и координатору (`tell-komu`, адресат — константа развёртки); сам шлюз ничего не сбрасывает. Счётчики живут в памяти процесса: перезапуск их забывает, а беседы, так и не дошедшие до удачного хода, остаются в таблицах до перезапуска. Pressure-warning journal тоже требует читателя; «строка есть» не означает, что человек её прочитал. Continuation mailbox имеет свой courier/channel consumer, placement не равен turn start.
Three consecutive model/mapping failures invoke a deployment alert helper whose path is fixed in code. Verify the command and its assigned recipient. Content-filter refusals (provider "flagged" texts) are counted as a separate kind: two of the same kind in a row, or one "this session", mark the conversation and send one "/new needed" signal per conversation to the operator (alert helper) and the coordinator (`tell-komu`, deployment constant); the gateway itself resets nothing. Counters live in process memory: a restart forgets them, and conversations that never succeed stay in the maps until restart. Pressure-warning logs need a reader too; an existing line does not prove human consumption. Continuation mailboxes have their own courier/channel consumers; placement is not turn start.

Ни один локальный fixture не доказывает действующую подписку.

Последние две пробы требуют runtime SDK/CLI. `stend-claude-mail-http`, `stend-claude-task-control` и `stend-guest-tools` берут слой `sdk-runtime` рядом с пакетом, если он читается учёткой; иначе — слой гостя `/opt/subscription-gateway-guest/sdk-runtime`; явно — `STEND_SDK=<каталог sdk-runtime>` (так же выбирает и `stend-env-dvizhka`). Выбор печатается строкой «слой SDK: …»; нечитаемый слой — СЛЕПОТА, код 2. Если слой взят не рядом с пакетом, эти три стенда сверяют версию `@anthropic-ai/claude-agent-sdk` слоя с `version` записи `claude-agent-sdk` в `/etc/agent-registry/plugins.yaml`: расхождение — код 1, реестр или версия не читаются — код 2. Compaction backend задаётся локальной фикстурой, API/token/bridge/дом/БД должны быть фикстурами во временном каталоге. Защита путей проверяет, что lexical/realpath остаются внутри fixture. Не передавайте боевой токен и production state в такие тесты. Запуск не должен менять gateway options, чтобы измерить «tools empty» только по настройке, а не вмешательством наблюдателя.
The last two tests require runtime SDK/CLI. `stend-claude-mail-http`, `stend-claude-task-control` and `stend-guest-tools` use the `sdk-runtime` layer next to the package if this account can read it; otherwise the guest layer `/opt/subscription-gateway-guest/sdk-runtime`; explicitly `STEND_SDK=<sdk-runtime directory>` (`stend-env-dvizhka` selects the same way). The compaction backend is a local fixture, API/token/bridge/home/database must be fixtures in a temporary directory. Path checks ensure lexical/realpath confinement. Never supply live tokens or production state. Do not alter gateway options to make tools empty; measure the setting, not observer interference.

Exit 0 means executed scenarios passed; 1 is a mismatch; 2 means missing prerequisites where the test implements that code. Новый stend-deployment-config проверяет реальный gateway process и HTTP с подставным SDK: выбранную/отсутствующую/ошибочную зависимость, явный статус, сохранность обычного хода, настройки адресов и Node SQLite. Физические history-пробы используют детерминированный backend fixture; проверяют вызывающий код и сохранение/очистку gateway, не алгоритм внешнего модуля. Synthetic pressure-events соблюдают шаг журнала 25000 токенов и сами пересекают порог.
The new stend-deployment-config exercises a real gateway process and HTTP with a fixture SDK: configured/missing/failed dependencies, explicit status, ordinary-turn survival, address settings and Node SQLite. Physical-history tests use a deterministic backend fixture; they verify gateway caller/preservation/cleanup behavior rather than the external module algorithm. Synthetic pressure-events respect the 25000-token logging step and actually cross the threshold.

Новый stend-memory-module-config гоняет исходный gateway caller с настоящим import fixture, наблюдает выбранный module path и реальную запись fixture на диск: configured/missing/bad/restored. Внешний memory backend и настоящая DB не участвуют. Code runner снимает code=result.returncode сразу, до обработки stdout/следующей команды; исход 2 не является зелёным.
The new stend-memory-module-config exercises the original gateway caller with native fixture import, observing its selected module path and an actual disk fixture receipt: configured/missing/bad/restored. It does not use an external memory backend or real DB. The code runner captures code=result.returncode immediately, before stdout processing or another command; exit 2 is not success.
