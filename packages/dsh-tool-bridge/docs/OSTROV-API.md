# ostrov_api — инструмент API Острова · The Ostrov API tool

Для копии стендов `tools/kopiya-ostrov-api.sh <архив> <релиз с vps-ru> <абсолютный каталог …/ostrov-api>` принимает две формы: прежнюю `candidate/app` + `deployment/manifest.json` и новую `app` + `manifest.json`. Архив может быть tar или tar.gz; сжатие определяется по содержимому. До замены копии сверяются artifact, все имена файлов и их SHA256. Лишний файл, неверный релиз/сумма, ссылка, опасный путь, повтор имени или неоднозначная форма дают отказ кодом 2. Установленная раскладка `app/`, `manifest.json`, `ISTOCHNIK` и страховка `.prezhnyaya` сохраняются. Сторож копии даёт строку вызова; исполняет назначенная рука. Проверка не доказывает равенство содержимого бою, если сайт изменили без нового release. Стенд установщика — `test/kopiya-ostrov-installer.mjs`, без живого сайта и боевого каталога.

Документ описывает инструмент `ostrov_api` версии пакета из `package.json`. Это описание поведения, а не объявление боевого монтажа: включение требует согласованных сервера API и моста и приёмки. Сайт (Site) получает только публичные catalog/objects/quote через согласованную политику канала.
This document describes the `ostrov_api` tool of the package version in `package.json`. It describes behaviour, not a production deployment: enabling it requires a matching API server and bridge and an acceptance check. The Site gets only the public catalog/objects/quote through the agreed channel policy.

`ostrovApi.enabled:true` регистрирует один инструмент с operation/params. Модель не задаёт context, route, senderId или requestKey. Разрешены catalog, objects, quote, identity; staff.list/read; client.list/read/create/save/assign; plan.list/create/read/edit/connections/link. Бронирование, заявки, CONFIRM, удаление и управление учётками сотрудников не входят в этот API.
`ostrovApi.enabled:true` registers one tool with operation/params. The model does not supply context, route, senderId or requestKey. Allowed: catalog, objects, quote, identity; staff.list/read; client.list/read/create/save/assign; plan.list/create/read/edit/connections/link. Bookings, requests, CONFIRM, deletion and staff account management are not part of this API.

## Текущий контекст и роли · Current context and roles

Для staff/client операций, plan.list/connections/link требуется текущий private Telegram update. Caller сверяет root agent, поколение, рабочий каталог ledger, незавершённые receipts текущего открытого turn, route_key и channel_sessions. Группа, A2A, смешанные отправители и отсутствие доказанного private update получают отказ. После HTTP повторно проверяются root/turn и исходный update; результат сменившемуся входу не выдаётся.
staff/client operations and plan.list/connections/link require the current private Telegram update. The caller checks the root agent, generation, the ledger working directory, unfinished receipts of the current open turn, route_key and channel_sessions. A group, A2A, mixed senders or no proven private update are refused. After HTTP the root/turn and the original update are checked again; a result is not handed to a changed input.

Гостевой режим следует из корневого маршрута, не слов модели. Гость Telegram может читать публичные рабочие поля staff.list/read, свою карточку и свои расчёты. SDK не делает staff identity probe для гостя, даже если его Telegram ID известен как сотрудник. Подтверждённые сервером manager/leader/hospitality на служебном private TG получают остальные CRM-операции. Принятый владельцем риск writable ledger остаётся: инструмент не добавляет криптографического доказательства update и защиты от той же OS-учётки.
Guest mode follows from the root route, not the model's words. A Telegram guest may read the public working fields of staff.list/read, their own card and their own quotes. The SDK does not probe staff identity for a guest even if their Telegram ID is known as staff. Server-confirmed manager/leader/hospitality on a service private TG get the other CRM operations. The owner-accepted risk of a writable ledger remains: the tool adds no cryptographic proof of the update and no protection against the same OS account.

`client.save` без id сохраняет свою карточку; с id — выбранную гостевую карточку по полномочиям сотрудника. `plan.create(clientId/clientProfile)` назначает сотрудника ответственным расчёта, не всей карточки. `client.assign` меняет ответственного всей цепочки. После записей требуется отдельное чтение; plan.list не показывает deleted, полный охват проверяет административная рука. Эскалация — только инструментом `pismo_rukovoditelyu` руководителю: выбор staff по directions не означает доставку ему.
`client.save` without an id saves one's own card; with an id — the selected guest card under the staff member's authority. `plan.create(clientId/clientProfile)` makes the staff member responsible for the quote, not the whole card. `client.assign` changes the person responsible for the whole chain. Writes need a separate read afterwards; plan.list does not show deleted plans, full coverage is checked by an administrative hand. Escalation goes only through the `pismo_rukovoditelyu` tool to the manager: choosing staff by directions does not mean delivery to them.

На wire профиль содержит name/phone/email/messengers/notes. Модельный messenger.userId может отсутствовать; SDK добавляет пустую строку после специальной обработки self-Telegram. Реальный sender применяется только к собственной карточке, не к Site или выбранному гостю. Явные подтверждённые ID сохраняются. Полный профиль сначала читают, затем меняют нужные поля.
On the wire a profile carries name/phone/email/messengers/notes. A model-supplied messenger.userId may be missing; the SDK adds an empty string after the special self-Telegram handling. The real sender applies only to one's own card, not to the Site or a selected guest. Explicit confirmed IDs are kept. A full profile is read first, then the needed fields are changed.

## Состояние повторов · Repeat state

Единственный allocator — savedKey и helper `tools/ostrov-request-state.mjs`. Все шесть write-операций (plan.create/edit, client.create/save/assign, plan.link; перечень `WRITES` в `src/ostrov-api.js`) проходят его до Python/HTTP. Сохраняются прежний canonical digest и legacy lookup; нового параллельного allocator нет. Digest включает root session id/createdAt, operation/params, actor, botId и режим; меняющиеся transport update/message IDs исключены. Ранее сохранённый исходный update используется для повтора.
The only allocator is savedKey and the `tools/ostrov-request-state.mjs` helper. All six write operations (plan.create/edit, client.create/save/assign, plan.link; the `WRITES` list in `src/ostrov-api.js`) pass through it before Python/HTTP. The former canonical digest and legacy lookup are kept; there is no new parallel allocator. The digest includes the root session id/createdAt, operation/params, actor, botId and mode; changing transport update/message IDs are excluded. A previously saved original update is used for a repeat.

`requestKeyDir` обязателен, абсолютен и расположен вне workspace. Прежде нового writer оператор явно готовит state по [OSTROV-REQUEST-RECOVERY.md](OSTROV-REQUEST-RECOVERY.md) при остановленном старом writer. Полнота старых случайных ключей — проверяемая оператором предпосылка; потерянные до bootstrap ключи код не угадывает. Автоматической инициализации, смены epoch или сброса guard нет.
`requestKeyDir` is required, absolute and outside the workspace. Before a new writer, the operator explicitly prepares the state per [OSTROV-REQUEST-RECOVERY.md](OSTROV-REQUEST-RECOVERY.md) with the old writer stopped. Completeness of the old random keys is an operator-verified precondition; keys lost before bootstrap are not guessed by the code. There is no automatic initialisation, epoch change or guard reset.

Отсутствующий/битый guard либо неполная известная пара key/reservation дают OSTROV_API_RECOVERY_REQUIRED до HTTP, чтения остаются доступны. После согласованной старой копии post-cutover без обеих записей тот же epoch+digest вычисляет тот же key; серверная идемпотентность предотвращает дубль при сохранённом серверном журнале. Это не обещание восстановления произвольной потери/отката обеих сторон. Полные границы и процедура — в [OSTROV-REQUEST-RECOVERY.md](OSTROV-REQUEST-RECOVERY.md).
A missing/broken guard or an incomplete known key/reservation pair gives OSTROV_API_RECOVERY_REQUIRED before HTTP; reads stay available. After a consistent old post-cutover copy lacking both records, the same epoch+digest computes the same key; server idempotency prevents a duplicate while the server journal is kept. This is not a promise to recover an arbitrary loss or rollback on both sides. Full limits and the procedure are in [OSTROV-REQUEST-RECOVERY.md](OSTROV-REQUEST-RECOVERY.md).

После неизвестного исхода нет автоматических повторов. Один последующий HTTP 400/409 не доказывает no-write предыдущего запроса и не разрешает новый ключ. Повторный старый результат не заменяет свежего чтения текущего состояния. Отдельная идентичная копия по тем же входу/данным не предусмотрена; совместная приёмка проверяет потерю state и поимённый серверный состав.
After an unknown outcome there are no automatic retries. A single later HTTP 400/409 does not prove that the previous request wrote nothing and does not permit a new key. A repeated old result does not replace a fresh read of the current state. A separate identical copy for the same input/data is not provided; joint acceptance checks state loss and the server-side inventory by name.

## Site и PDF · Site and PDF

Site, включая закреплённые site-* с ротированным session ID, получает только catalog/objects/quote с guest=true без Telegram actor, Site DTO и requestKey. Эти операции ничего не сохраняют; identity, CRM и все сохранённые планы отказаны до HTTP. Root/createdAt/turn/openTurn и закреплённый Site route повторно сверяются после ответа. SDK сохраняет историческую подпись результата route=guest-telegram: это метка публичного транспорта, не Telegram identity. Для карточек, сохранения планов и их ссылок по-прежнему нужны отдельные producer/namespace/restore и Site DTO; инструмент их не подключает.
The Site, including pinned site-* sessions with a rotated session ID, gets only catalog/objects/quote with guest=true and no Telegram actor, Site DTO or requestKey. These operations save nothing; identity, CRM and all saved plans are refused before HTTP. Root/createdAt/turn/openTurn and the pinned Site route are re-checked after the answer. The SDK keeps the historical result label route=guest-telegram: it marks the public transport, not a Telegram identity. Cards, saved plans and their links still need a separate producer/namespace/restore and a Site DTO; the tool does not connect them.

Обычный quote возвращает Q в result. Сохранённые plan.create/read/edit возвращают полный D с kind/quote/url/updatedAt. PDF-инструменту передают либо quote:Q с kind, либо result:D; не внешний SDK-конверт и не оба поля. Telegram PDF/отправка требуют реально подключённых канальных инструментов и настроенных бланков. Наличие Telegram-инструмента не доказывает отправку PDF на сайт.
A plain quote returns Q in result. Saved plan.create/read/edit return the full D with kind/quote/url/updatedAt. The PDF tool gets either quote:Q with kind or result:D — not the outer SDK envelope and not both fields. Telegram PDF/sending needs channel tools actually connected and letterheads configured. Having a Telegram tool does not prove a PDF was sent to the site.
