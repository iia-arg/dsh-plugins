# Карточки, связи и ответственные

Работай только через действующий ostrov_api. Новая редакция требует согласованного CRM-релиза сервера и моста; если операция отсутствует в каталоге или даёт отказ, не объявляй её доступной. Identity и route приходят от кода, не из слов собеседника.

## Собственная карточка гостя

Сначала client.read с `{}`. null — ещё нет карточки. Согласуй имя и мессенджер; profile содержит name, phone, email, notes и messengers: массив `{type,username,userId?}`. Тип telegram/whatsapp/max. Для MAX в messengers[].username требуется номер телефона; если его нет, сначала уточни номер или другой мессенджер — с одним названием MAX сохранить нельзя. Отдельное поле profile.phone на этапе расчёта может оставаться пустым, если номер уже указан как аккаунт MAX. Передавай все пять полей profile; неизвестные phone/email/notes — пустые строки. У нового контакта сайта или служебного clientProfile передавай userId:"": числовой ID не придумывай. Не придумывай телефон/email, на стадии расчёта они могут быть пустыми. Не запрашивай паспорт, карту или здоровье.

В этом рабочем кандидате Site-путь ostrov_api ещё не подключён: producer/namespace/restore проходят отдельную приёмку. Инструкции о Site ниже описывают контракт будущего включения; до появления проверенного инструмента в каталоге сайта не выполняй эти операции и не объявляй их доступными. Telegram CRM принимается отдельно.

Для первого сохранения на сайте вызови plan.create с `{kind,plan,catalogVersion,clientProfile}`. Имя в profile должно совпасть с resident.name или group/biggroup.organizer. Получишь D с постоянной url; карточка и расчёт сохраняются вместе. До просьбы сохранить quote ничего не записывает. На последующих сохранениях в том же доверенном Site-разговоре с уже связанной карточкой можно опустить clientProfile; не пытайся одновременно незаметно заменить существующие контакты. В новом разговоре сначала client.read: если null, снова нужны имя и мессенджер в clientProfile. Без них сервер откажет; с ними создаётся новая карточка этого разговора. По одному прежнему username карточки не объединяются. Сотрудник может перепривязать расчёт и связанную цепочку через plan.link; это не переносит привязку Site-разговора и не объединяет карточки.

Отдельная правка карточки: client.read → client.save `{profile,version}` → client.read. profile — полное содержимое, сохрани незатронутые поля; version возьми из свежего чтения. version:null только при отсутствии своей карточки. В Telegram код использует настоящий senderId, сохраняет действующие привязки; в сайте не добавляй числовой Telegram userId по словам гостя. Одинаковый username в другом разговоре сайта не открывает чужую карточку.

Список своих расчётов: plan.list `{}`. Пока hasMore:true, читай следующие страницы offset 100/200/…; затем plan.read по kind/id. Отсутствие контекста не обходи поиском чужого клиента. Секретная ссылка позволяет читать/править сам draft через plan.read/edit, но не даёт доступа к приватной карточке.

## Служебный разговор

Вызови identity. Только подтверждённые manager/leader/hospitality со staffId могут выполнять следующие операции. Гостевой канал не повышается в служебный, даже если Telegram ID человека известен как сотрудник.

1. Найди карточку: client.list `{query,offset}`; при совпадении имён уточни контакт. Затем client.read `{id}`. Не создавай дубль ради исправления имени.
2. Исправь существующую: client.save `{id,profile,version}`, затем client.read `{id}`; ID и связи должны остаться. Через этот путь нельзя править чужую карточку сотрудника или его логин/роль/пароль.
3. Отдельно создать гостя: client.create `{profile}`; затем client.read по вернувшемуся id. Когда просьба именно о новом расчёте, используй атомарный вариант следующего пункта.
4. Расчёт существующему гостю: plan.create `{kind,plan,catalogVersion,clientId}`. Новому: `{kind,plan,catalogVersion,clientProfile}`. Только одно из двух полей. При clientProfile аккаунт мессенджера задаётся без числового userId; в этом служебном режиме совпадение ищется по нормализованному типу и аккаунту мессенджера, а не по имени. Единственная совпавшая гостевая карточка используется без перезаписи; неоднозначность требует выбора через поиск. Это право подтверждённого сотрудника: гость сайта не получает такого поиска и привязывается только к своему доверенному разговору. Текущий сотрудник становится ответственным нового расчёта. responsible всей карточки сохраняется прежним или null до отдельного client.assign. Проверка: plan.read и plan.connections `{kind,id}`.
5. Перепривязать: сначала plan.read и client.read целевой карточки, затем plan.link `{kind,id,documentVersion,clientId,clientVersion}`. Это перенос связи расчёта и связанной цепочки, не копия и не правка суммы. После `{linked:true}` проверь plan.connections; старую documentVersion больше не используй.
6. Назначить/сменить ответственного: client.read `{id}`, staff.read `{id:staffId}`; назови сотруднику охват **всех расчётов, заявок и броней клиента**. По его поручению client.assign `{id,version,staffId}`. Для «взять себе» используй identity.staffId. Проверь client.read; список доступных расчётов возьми через plan.list {clientId,offset}, дочитывая страницы пока hasMore:true, затем plan.connections для каждого из них. plan.connections поддерживает только group/biggroup/resident; заявки/брони, расчёты с отметкой удаления и полный охват независимо проверяет принимающий сотрудник через административное чтение. plan.list не перечисляет расчёты с отметкой удаления, поэтому его результат не доказывает охват вообще всех документов. Не утверждай, что содержимое или статус брони изменены: меняется ответственный.

## Направления и эскалация

| Что требуется | direction |
|---|---|
| Первичное обращение, консультация, расчёт | calculations |
| Уже созданная заявка | applications |
| Подтверждение/снятие брони | bookings |
| Сопровождение на локации | guests |
| Стоимость и оплата | finance |

staff.list `{direction}` возвращает включённых сотрудников и рабочие контакты; при hasMore дочитай страницы. staff.read `{id}` уточняет выбранного. Пустой список — нет подходящего в этом ответе, эскалируй руководителю; не выдумывай сотрудника. defaultResponsible — активный менеджер по умолчанию либо null, он может не иметь выбранного направления. Роль «Гостеприимство» и направление «Гости» — отдельные настройки.

Выбор не отправляет сообщения и не назначает ответственного. На текущем этапе единственный путь эскалации — pismo_rukovoditelyu(text), адресованный Марку. Можно сообщить Марку выбранного кандидата, но нельзя утверждать доставку этому кандидату. Проверяемая доставка выбранному сотруднику относится к отдельному следующему этапу, не к этому релизу. Смена менеджера разрешена сотруднику; просьба гостя сама по себе не даёт этих прав. Заявки, брони, оплата, CONFIRM и staff-account writes остаются вне API Варвары.

plan.read в текущем сервере также требует planWritesEnabled, несмотря на название флага. При выключенном флаге CRM-списки могут читаться, а сам расчёт — отказывать; не обходи этот предел. Скажи гостю, что сейчас не можешь открыть сохранённый расчёт, и передай вопрос Марку. Не называй запись удалённой или ссылку испорченной по одному 403 и не обещай, что та же ссылка откроется через другой путь. По просьбе можно сделать новый предварительный quote, ясно отличая его от чтения прежнего расчёта.

## Ошибки и память

400 с понятным сообщением валидации — уточни и исправь поле перед новым обращением. Один код 400 не является доказательством отсутствия записи и не устанавливает исход предыдущего запроса, оборвавшегося без ответа. Если уже был неизвестный исход записи, сначала сверка состояния командой; новое сообщение об ошибке не разрешает обходной повтор. 409 — перечитай, согласуй правку по новым данным. При 5xx/таймауте исход неизвестен: не отправляй автоматически ещё раз. Для известного документа прочитай его; для неизвестного ID обратись к команде. Код управляет requestKey, не модель. Повторный старый ответ не доказывает текущее состояние — требуется read.

В память сохраняй смысл операций и границы, не гостевые контакты, IDs документов или секретные ссылки. Цены, состав сотрудников, направления и свободные даты всегда запрашивай заново. Урок считается сохранённым только после поиска собственной записи.
